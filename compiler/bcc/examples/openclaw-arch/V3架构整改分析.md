# OpenClaw V3 架构整改分析

> 基于 bcc arch validate 的 V0→V3 全量分析，针对 target 门禁 FAIL 的 15 条违规边，
> 给出根因归类、整改方案和优先级排序。

## 1. 现状概要

| 指标 | 实际值 | 目标上限 | 差距 |
|------|--------|----------|------|
| 模块间有向边数 | 42/56 | ~22 | 需砍掉 ~20 条边 |
| 有向密度 | 75% | 40% | 超标 35pp |
| 双向耦合对数 | 20 | 5 | 超标 15 对 |
| unexpected 边 | 10 条 / 442 文件级 | 0 | 全部需要整改 |
| forbidden 边 | 5 条 / 26 文件级 | 0 | 全部需要消除 |
| missing 边 | 0 | 0 | 唯一达标项 |

**核心发现**：代码里的依赖关系几乎"全连接"，8 个模块只有 14 条边不存在。
架构上理想分层是单向依赖、密度 40% 以下，现实离此差距巨大。

## 2. 根因归类

分析 15 条违规边（10 unexpected + 5 forbidden），按根因归为 **4 类问题**：

### 问题 A：ops_client_entry 被当成公共工具库（7 条边，194 文件级）

**现象**：几乎所有模块都反向依赖 ops_client_entry，引用的是 CLI 格式化工具、
解析器、web/wizard 工具等本应属于公共层的代码。

| 违规边 | 文件级边数 | 引用目标（采样） |
|--------|-----------|-----------------|
| foundation_infra → ops_client_entry | 44 | `cli/command-format.ts`, `cli/parse-duration.ts` |
| channel_ingress → ops_client_entry | 41 | `web/media.ts`, `wizard/prompts.ts` |
| gateway_control_plane → ops_client_entry | 37 | `cli/deps.ts`, `commands/agent.ts` |
| plugin_tool_extension → ops_client_entry | 32 | `web/media.ts`, `cli/parse-duration.ts` |
| agent_runtime → ops_client_entry | 27 | `cli/command-format.ts`, `cli/parse-duration.ts` |
| platform_hosts → ops_client_entry | 8 (forbidden) | `terminal/theme.ts`, `cli/command-format.ts` |
| external_dependencies → ops_client_entry | 5 (forbidden) | `cli/command-format.ts`, `commands/models/shared.ts` |

**根因**：`ops_client_entry` 是 450 文件的"大杂烩"，入口逻辑和公共工具混在一起。
底层模块需要格式化/解析能力，只能反向 import 这个顶层模块。

### 问题 B：foundation_infra 上行依赖（3 条边，133 文件级）

**现象**：基础设施层反向依赖了通道层、网关层和插件层。

| 违规边 | 文件级边数 | 引用来源（采样） |
|--------|-----------|-----------------|
| foundation_infra → channel_ingress | 91 | `infra/outbound/outbound-session.ts`, `infra/outbound/deliver.ts` |
| foundation_infra → gateway_control_plane | 40 | `security/audit.ts`, `infra/outbound/outbound-session.ts` |
| foundation_infra → plugin_tool_extension | 7 (forbidden) | `config/validation.ts`, `infra/outbound/message-action-runner.ts` |

**根因**：`infra/outbound/` 子目录下的消息投递逻辑直接引用了 channel 和 gateway 的实现。
这些投递逻辑按职责应该属于网关或通道层，而非基础设施层。
`session-key` 工具被放在 gateway 下但被 infra 广泛引用，位置不对。

### 问题 C：plugin ↔ channel 直连（1 条边，121 文件级）

**现象**：插件层直接 import 通道层的类型和实现。

| 违规边 | 文件级边数 | 引用来源（采样） |
|--------|-----------|-----------------|
| plugin_tool_extension → channel_ingress | 121 | `plugin-sdk/index.ts`(60), `plugins/runtime/index.ts`(37) |

**根因**：`plugin-sdk/index.ts` 和 `plugins/runtime/index.ts` 两个 barrel 文件
大量 re-export 通道层的类型，造成 121 条边中 97 条来自这两个文件。
实际上是 barrel export 导致的"传染式"耦合，而非真正的业务依赖。

### 问题 D：外部/宿主层的分层违规（4 条边，21 文件级）

**现象**：`external_dependencies` 和 `platform_hosts` 反向依赖上层。

| 违规边 | 文件级边数 | 类型 | 引用来源（采样） |
|--------|-----------|------|-----------------|
| external_dependencies → agent_runtime | 2 | forbidden | `providers/github-copilot-auth.ts` → `agents/auth-profiles.ts` |
| external_dependencies → foundation_infra | 7 | unexpected | `providers/github-copilot-*.ts` → `config/logging.ts`, `infra/json-file.ts` |
| platform_hosts → agent_runtime | 4 | forbidden | `node-host/runner.ts` → `media/mime.ts` |
| foundation_infra → platform_hosts | 2 | unexpected | `infra/restart.ts` → `daemon/constants.ts` |

**根因**：provider adapter 直接引用了 runtime 的 auth-profiles 和 infra 的 config/log；
host 层直接引用了 runtime 的 media 工具。都是缺少抽象接口导致的反向依赖。

## 3. 整改方案

### 方案一：抽取 shared_kernel（解决问题 A，砍 194 条边）

**优先级：P0 — 效果最大，影响面最广**

**做法**：

1. 在 ops_client_entry 中识别被底层模块引用的公共模块，主要是：
   - `cli/command-format.ts` — 被 5 个模块引用
   - `cli/parse-duration.ts` — 被 4 个模块引用
   - `web/media.ts` — 被 3 个模块引用
   - `wizard/prompts.ts` — 被 2 个模块引用
   - `terminal/theme.ts` — 被 2 个模块引用
   - `cli/deps.ts` — 被 2 个模块引用

2. 将这些文件移到 `foundation_infra`（或新建 `shared_kernel` 模块）

3. 所有引用方改为从新位置 import

**预期效果**：
- 消除 7 条违规边中的 5~6 条（forbidden 的 2 条也能解决）
- 减少约 194 条文件级依赖边
- 双向耦合减少约 5~6 对

**风险**：ops_client_entry 内部的 barrel export（`index.ts`）可能导致连锁修改，
需逐文件确认实际引用链。

### 方案二：拆分 infra/outbound（解决问题 B，砍 133 条边）

**优先级：P1 — 结构性整改**

**做法**：

1. 将 `infra/outbound/` 整个子目录移到 `gateway_control_plane` 或独立为
   `message_delivery` 模块，因为消息投递本质上是网关/通道的职责

2. 将 `routing/session-key.ts` 从 gateway_control_plane 下沉到 foundation_infra，
   因为它是被多个模块广泛引用的基础工具（被 infra、channel、plugin 共 70+ 次引用）

3. 删除 `config/validation.ts` → `agents/tools/common.ts` 的直接引用，
   用接口替代

**预期效果**：
- 消除 3 条违规边（含 1 条 forbidden）
- 减少约 133 条文件级依赖边
- foundation_infra 回归"纯基础设施"定位

### 方案三：拆 barrel export（解决问题 C，砍 121 条边）

**优先级：P1 — 投入小、回报大**

**做法**：

1. 拆分 `plugin-sdk/index.ts`（贡献 60 条边）和 `plugins/runtime/index.ts`（37 条边）
   的 barrel export

2. 将这两个文件中 re-export 的 channel 类型改为：
   - 在 plugin 层定义 channel 的抽象接口（port）
   - 通道层实现该接口（adapter）
   - barrel 文件只 export 自己模块的内容

**预期效果**：
- 消除 1 条 unexpected 边（121 条文件级）
- 这是单条边文件级数量最大的违规，修 2 个文件就能解决大部分

### 方案四：引入 Port 接口（解决问题 D，砍 21 条边）

**优先级：P2 — 文件少但方向性重要**

**做法**：

1. **Provider auth port**：在 foundation_infra 定义 `AuthPort` 接口，
   `external_dependencies` 的 provider 依赖该接口而非直接 import runtime 的
   `auth-profiles.ts`

2. **Host protocol port**：在 foundation_infra 定义 `HostPort` 接口，
   `platform_hosts` 通过该接口获取 runtime 能力，而非直接 import `media/mime.ts`

3. **Restart contract**：将 `daemon/constants.ts` 中被 infra 引用的常量
   提取到 foundation_infra 层

**预期效果**：
- 消除 4 条违规边（含 3 条 forbidden）
- 文件级影响小（21 条），但修正了分层方向

## 4. 执行顺序和预期指标

| 阶段 | 方案 | 砍掉的边 | 累计密度 | 累计双向对 |
|------|------|----------|----------|------------|
| 现状 | — | — | 75% | 20 |
| 第一阶段 | A: 抽 shared_kernel | ~194 文件 / 5~6 条模块边 | ~55% | ~14 |
| 第二阶段 | B: 拆 outbound + C: 拆 barrel | ~254 文件 / 4 条模块边 | ~43% | ~8 |
| 第三阶段 | D: 引入 Port | ~21 文件 / 4 条模块边 | ~40% | ~6 |

三个阶段做完后预期：
- unexpected_edges: 10 → 0~2
- forbidden_edges: 5 → 0
- density: 75% → ~40%（达标）
- bidirectional: 20 → ~6（接近目标 5）

## 5. 验证方法

每个阶段完成后运行：

```bash
bcc arch validate \
  --target seed/v3.target-matrix.yaml \
  --transition seed/v3.transition-matrix.yaml \
  --gates seed/v3.gates.yaml \
  --actual artifacts/relation_matrix.actual.json \
  --out-dir versions/v3.1-draft \
  --fail-on-gate

# 对比前后
diff versions/v3-draft/gate-evaluation.tsv versions/v3.1-draft/gate-evaluation.tsv
```

第一阶段完成后应该能看到 transition 的 `max_forbidden_edges_count` 可以收紧，
最终目标是 target 门禁全 PASS。

## 附录：transition 门禁的局限性

V3 的 transition 门禁阈值（`gates.yaml`）是按现状倒推的：

```yaml
transition:
  max_forbidden_edges_count: 5    # = 实际 5
  max_forbidden_total_edges: 26   # = 实际 26
  max_directed_density_pct: 75    # = 实际 75
  max_bidirectional_pair_count: 20 # = 实际 20
```

每一项都刚好等于现状值。这意味着 transition PASS 只证明"没有变更糟"，
不证明"架构已经 OK"。

整改过程中应逐步收紧 transition 阈值：
- 第一阶段完成后收紧到 `density: 55, bidirectional: 14`
- 第二阶段完成后收紧到 `density: 43, bidirectional: 8`
- 最终 transition 阈值与 target 对齐，两套门禁合一
