# BDD 指令集注解规范（@bdd）

目的：把“可编译的指令 spec”需要的人类决策信息（scope/boundary/输出/枚举等）写回到正经 API 代码旁边，让脚手架可以接近全自动生成 `InstructionRegistry` 草稿。

这不是替代 `InstructionRegistry`，而是让 `InstructionRegistry` 的维护成本变低、减少猜测与重复搬运。

## 基本约定

- 每个“对外 API 边界函数”（HTTP/Application Service/Service/Domain Service）都可以选择声明 `bdd(...)` 注解。
- `bdd(...)` 必须紧贴目标 `def/defp` 之前（中间不要插入其他 `@attr`），保证绑定到正确函数。
- 注解只用于测试指令生成与校验，不影响业务逻辑。

## 代码写法

在模块里启用注解采集：

```elixir
defmodule Shop.SomeModule do
  use Shop.BDD.Annotations

  bdd instruction: :my_instruction,
      kind: :when,
      version: :v1,
      boundary: :service,
      scopes: [:unit, :integration, :e2e],
      args: %{
        supplier_id: %{type: :uuid, required?: true},
        status: %{type: :string, required?: true, allowed: ["paid", "pending"]}
      },
      outputs: %{settlement_no: :string},
      rules: [],
      async?: false,
      eventually?: false,
      assert_class: nil
  def create_monthly_settlement(%{supplier_id: supplier_id, status: status}) do
    ...
  end
end
```

## 字段说明

所有字段都是可选的（未写就由脚手架/默认规则补齐）。

- `instruction`：指令名（atom 或 string）。不填则脚手架默认用 `#{prefix}_#{function_name}`。
- `kind`：`:given | :when | :then`。
- `version`：`:v1 | :v2`。
- `boundary`：`:http | :service | :domain | :db | :event | :external_io | :test_runtime | nil`（与 `InstructionRegistry` 一致）。
- `scopes`：允许的测试层级，`[:unit, :integration, :e2e]` 的子集。
- `args`：参数 spec 覆盖（或补充）。结构与 `InstructionRegistry` 一致：
  - `type`：`:uuid | :datetime | :date | :decimal | :int | :string | :bool`
  - `required?`：是否必填
  - `allowed`：允许的枚举值列表（string 列表）
- `outputs`：输出 spec（写入 BDD ctx 的 key 与类型），结构与 `InstructionRegistry.outputs` 一致。
- `rules`：编译期规则（例如 `{:exactly_one_of, [:a, :b]}`），结构与 `InstructionRegistry` 一致。
- `async?`：该指令是否可能异步触发副作用（用于 lint/策略）。
- `eventually?`：是否需要 eventually 语义（用于 lint/策略）。
- `assert_class`：断言等级标记（A/B/C/D/weak/error 等），用于 lint/策略。

## 与脚手架生成器的关系

脚手架生成器 `bddc registry.scaffold --project-root /home/wangbo/document/shop ...` 的行为（兼容：`mix bdd.registry.scaffold`；说明：`bddc` 等价于 `bdd_compiler`）：

- 会先从源码 AST 抽取函数头里的 map/struct pattern key，作为“默认必填 args”。
- 如果检测到模块实现了 `__bdd_defs__/0`（即 `use Shop.BDD.Annotations`），就会把注解里的：
  - `kind/boundary/scopes/version/outputs/rules/...` 合并到草稿里
  - `args` 会与 AST 推断结果做 merge：注解优先（可改 type、allowed、required?）

## 注解完整性检查（强制门禁）

为了达到“100% 自动生成（不靠默认值/猜测）”，建议在生成指令 spec / 生成测试前先跑：

```bash
bddc annotations.check --project-root /home/wangbo/document/shop
# 兼容：mix bdd.annotations.check
```

该任务会检查所有 `use Shop.BDD.Annotations` 的模块，确保每条 `bdd(...)` 注解显式写全关键字段：
`instruction/kind/boundary/scopes/args/outputs/rules/async?/eventually?/assert_class`，以及 `args.*` 的 `type/required?`。

## 自动写回指令 spec（可选）

当注解齐全并通过 `bddc annotations.check --project-root /home/wangbo/document/shop`（兼容：`mix bdd.annotations.check`）后，可以用：

```bash
bddc registry.upsert --project-root /home/wangbo/document/shop --module <模块> --functions f/1,g/2 --prefix <前缀> --kind when --version v1
# 兼容：mix bdd.registry.upsert --module <模块> --functions f/1,g/2 --prefix <前缀> --kind when --version v1
```

写回方式取决于项目是否提供 mix task（`bddc` 会自动选择）：
- wrapper：走 `mix bdd.registry.upsert`，将 spec upsert 到 `Shop.BDD.InstructionRegistries.Generated`（`lib/shop/bdd/instruction_registries/generated.ex`），避免自动改写大字典造成冲突。
- standalone：写入 `priv/bdd/instructions_v1.exs` 的 `BDDC GENERATED` 标记区块（只覆盖标记区块，不改手写部分）。

## 推荐实践（让它更接近全自动）

- Application Service 入口参数尽量使用 `%{...}` 或 command struct，并在函数头 pattern 里写清 key（这样“必填参数”自动确定）。
- 为每个对外 API 都写 `@spec` 或明确的注解 `args.type`，避免类型只能退化成 `:string`。
- 枚举值（allowed）优先通过注解声明，避免靠静态分析 case/validation 反推。
